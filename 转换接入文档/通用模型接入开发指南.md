# EdgeForge 通用模型接入开发指南

本文以 Sophon 的 LPRNet 接入为例，说明如何在没有专人辅助时，把一个新模型接入转换工作台。目标是完成一条可复现的完整链路：

```text
原始训练权重 → 模型官方导出器 → ONNX → 厂商编译器 → RKNN/BModel → 可安装 SDK → 板端推理验收
```

只生成 ONNX 不算接入完成；必须同时有结构化 SDK 后处理和真实设备验收。

## 1. 先查清楚模型契约

从芯片厂商 Model Zoo 或官方 Demo 开始，记录以下内容：

- 原始权重格式（`.pt`、`.pth`、`.pdparams` 等）；
- 官方导出入口、依赖版本和输出节点；
- 输入布局、尺寸、颜色顺序、均值和缩放；
- 输出布局及后处理算法（例如 NMS、CTC、mask、关键点）；
- 目标芯片和精度限制；
- 官方测试图片、标签或词表。

例如 LPRNet 官方 Demo 明确规定输入为 `[1,3,24,94]`，输出为 `[batch,68,18]`，后处理为 CTC 解码；BM1684 不支持 FP16，因此平台精度只能提供 F32/INT8。

## 2. 找到代码落点

一个模型通常需要修改这些位置：

| 文件 | 作用 |
| --- | --- |
| `server/catalog.py` | 页面名称、原始权重格式、平台、精度和可用状态 |
| `server/sophon_models.py` | Sophon Demo 名称、BModel 名称、输入尺寸和组件信息 |
| `server/exporters.py` | 原始权重到厂商友好 ONNX 的路由 |
| `server/*_export_worker.py` | 需要独立依赖或官方 Python 网络定义时的隔离导出脚本 |
| `server/backends/bmodel.py` / `rknn.py` | ONNX 到 BModel/RKNN 的编译规则 |
| `sdk_template/edgeforge_sdk/model.py` | 预处理、`infer_raw()` 和结构化后处理 |
| `pipeline.py` | SDK 类名、示例输入和多模型打包规则 |
| `scripts/setup_wsl.sh` | 新仓库或新导出环境的可重复安装 |

只改页面下拉框而没有导出器或 SDK，会造成“看起来支持、实际不能用”，必须避免。

## 3. 新增模型目录能力

在 `catalog.py` 的 `_item(...)` 中登记模型。Rockchip 和 Sophon 可以分别声明：

```python
_item(
    "example", "Example", "目标检测", source="pt",
    input_size=[640, 640], weight_formats=(".pt",),
    exporter_ready=True, postprocess_ready=True, verified=False,
    sophon_platforms=("bm1684", "bm1684x"),
    sophon_precisions=("f32", "f16", "i8"),
)
```

`verified=True` 只在真实板端验收后设置。Sophon 的配置另写入 `SOPHON_MODELS`，包括 `sample`、`bmodel_name`、输入尺寸和多组件名称。

## 4. 编写专用导出器

不要把用户上传的 ONNX 当作公开入口，也不要使用一个通用 PyTorch 导出命令替代官方导出器。应在 `ArchitectureExporters.export()` 中按架构分支：

1. 检查原始后缀；
2. 调用官方仓库的网络定义或 exporter；
3. 把产物复制到任务私有目录的 `model.onnx`（多模型返回字典）；
4. 写入 `export_metadata.json`；
5. 由流水线统一执行 ONNX 结构校验。

若官方仓库依赖与工作台冲突，新增 `server/*_export_worker.py`，由独立 Python 子进程执行，并在 `setup_wsl.sh` 创建专用 venv。导出器失败时要保留子进程末尾日志。

LPRNet 的实际做法是调用 `vendor/sophon-demo/sample/LPRNet/tools/LPRNet.py`，用专用 worker 构造 68 类网络，再导出固定 `[1,3,24,94]` ONNX。

## 5. 接入厂商编译

### Sophon

`BModelBackend` 会依次执行：

```text
model_transform.py → MLIR →（可选校准）→ model_deploy.py → .bmodel
```

需要确认：

- `--chip` 使用 `bm1684` 或 `bm1684x`；
- `--quantize` 与芯片支持一致；
- 输入 shape 与导出的 ONNX 一致；
- INT8 任务要求用户提供校准图片 ZIP。

### Rockchip

按同样原则在 RKNN backend 中配置输入布局、均值、量化数据集和输出后处理，不要把 Sophon 参数混入 RKNN 分支。

## 6. 实现 SDK

在 `model.py` 中完成：

- `preprocess(source)`：读图/音频、缩放、归一化，返回输入和上下文；
- `infer_raw(inputs)`：只负责调用芯片运行时，返回原始输出；
- `postprocess(outputs, context)`：输出稳定的数据类对象；
- `predict(source)`：串起上述三步。

在 `pipeline.py` 的 `SDK_CLASSES` 登记显式类名，并让生成的 `example.py` 只调用 `edgeforge_sdk`，官方代码只能放在 ZIP 的 `reference/`。

LPRNet 的 SDK 返回 `TextRecognition(text, score, token_ids)`，其中 `text` 是 CTC 去重和去 blank 后的车牌字符串。

## 7. 测试顺序

先做不依赖芯片的检查：

```bash
python -m pytest -q
python -m py_compile server/sophon_lprnet_export_worker.py
```

再做完整任务：

```text
.pth → 官方 exporter → ONNX checker → TPU-MLIR → BModel → SDK ZIP
```

最后在对应板端新建项目 venv，安装 SDK，运行生成包的 `example.py`。至少检查：

- 模型能被运行时加载；
- 输出 shape 与官方 Demo 一致；
- 结果不是空值或随机乱码；
- SDK 的结构化结果与官方脚本基本一致；
- BM1684 和 BM1684X 的精度选择符合官方限制。

验收证据应记录任务 ID、芯片、精度、输入文件、结果和时间。确认无误后再把目录的 `verified` 改为 `True`，并单独提交 Git：

```bash
git add server sdk_template 转换接入文档
git commit -m "feat: add <model> Sophon conversion workflow"
```

## 8. 常见失败定位

| 现象 | 优先检查 |
| --- | --- |
| 页面没有模型 | `catalog.py` 是否登记，前端是否读取 `/api/catalog` |
| 上传后提示后缀不支持 | `weight_formats` 与 `exporters.supports()` 是否一致 |
| 导出找不到 ONNX | 官方 exporter 的工作目录、输出文件名和独立 venv |
| BModel 编译失败 | TPU-MLIR 是否在 PATH、chip/shape/precision 是否匹配 |
| SDK 能加载但结果错误 | 颜色顺序、NCHW/NHWC、输出顺序和后处理算法 |
| 板端 import 失败 | 板端运行时（SOPHON-SAIL 或 RKNNLite）是否安装在项目 venv |

## 9. 完成标准

模型只有在“专用导出器、ONNX 校验、目标边缘模型、结构化 SDK、示例、真实板端验收”全部完成后，才可以在工作台标记为可交付。否则应保留为“待真实验收”，并在 `notes` 中写明缺口。
